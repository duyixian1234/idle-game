# 自动攻占批量发起（auto-conquest-batch）

自动攻占同一冷却周期内（60s）在军力充足时**批量发起多个目标**（守卫升序逐目标判定，军力不足 break），直到军力/经济资源自然耗尽。不动冷却时长与守卫/保底/返还数值锚点，纯吞吐提升。

**状态**: Accepted（2026-08-12 spec：自动攻占批量发起，issue #20）
**证据**: `src/engine/conquest.ts:304-353`（autoConquestTick 批量循环）；`src/engine/balance.ts:290-297`（AUTO_CONQUEST_COOLDOWN_MS / RESERVE_PCT 未动）；`src/engine/conquest.test.ts`「批量发起」describe（6 例）+ 既有 5 例适配；`src/engine/offline.ts:112-118`（离线按冷却周期批量推进）

## 背景

1. **真实存档模拟暴露吞吐瓶颈**：`tmp/idle-save-2026-08-12.json`（NG+3，infinite，78 待攻占积压）跑 5000 tick（≈3.47 天）——军力产能 9546/s、守卫 = 容量/3 = 13.36万，军力 40s 即回满容量，**军力不构成瓶颈**；积压消化的真正上限是 `autoConquestTick` "每冷却周期只发 1 个目标"（成功即 `return`）的实现语义。
2. **军力保底 + 守卫双上限已保证回充节奏**（ADR-0033/0051）：守卫锚 40s 产出、回充 40s < 冷却 60s——军力在产能正常/过剩档恒充足，批量发起不增加"军力不够"的风险，只释放被实现语义压制的吞吐。

## 决策

1. **批量发起（不动冷却时长）**：`autoConquestTick` 成功分支从 `return [log]` 改为 `logs.push(...)` 继续扫下一个候选；循环后若 `logs.length > 0` 统一 `cfg.lastActionAt = nowMs`（冷却判定在函数入口，批量 = 一次冷却内多目标）。
2. **军力不足 break**：候选已按守卫升序（`consumeOf` 主序），当前打不起则后续守卫更大更打不起——单调屏障，continue 无意义。
3. **经济费不足 continue + pausedAt**：资源费（costMineral/costEnergy）非单调，后续目标资源费可能更低，保留跳过后重试语义。
4. **无显式批量上限**：军力保底逐目标判定 + 资源费快照双重自然约束，一次冷却上界 = 军力可支持的发起数（主档实测 2-3 个/60s）——防 Speculative Generality。
5. **纯吞吐提升、零规则变更**：冷却 60s、保底 10%、守卫公式、返还率 50% 全部不动（ADR-0033/0051/0056 锁定）；仅 `autoConquestTick` 发起逻辑变更。
6. **离线自动继承**：`settleOffline` 已按冷却周期循环调用同一函数（`offline.ts:114-117`），批量语义自动生效，在线/离线一致。

## 为什么

- 吞吐上限从 1 目标/60s 提升至军力/守卫（主档 ≈ 3 目标/60s）——积压消化速率显著改善，且随军力增长自然放大（军力越多一次打得越多），无需玩家手动干预。
- 军力不足 break + 保底逐目标判定双保险：raid/探索军力安全垫恒存（军力 ≥ 容量×10%），批量不会耗尽防御军力（US2/US6）。
- 与 ADR-0056 返还协同：批量 → 更多成功结算 → 返还更频繁，但返还率 50% < 100% 保证军力净耗恒正（balance-sim 三档永续性已断言），无印钞。

## 后果

- **UI**：零变更——批量复用既有 `cq.5` 日志逐条输出，无新面板/新交互。
- **schema**：零变更——`autoConquest.lastActionAt`/`pausedAt` 语义不变，无迁移。
- **测试**：`conquest.test.ts` 新增「批量发起」describe 6 例（军力充足全发/部分发后 break/首个 break/经济跳过/离线同口径/lastActionAt）；既有 5 例"每 tick 只发 1 个"断言适配为批量语义（意图保留：优先级/冷却协同/进行中跳过/平局打破/离线）。
- **平衡**：吞吐提升不改变单目标 ROI；军力净耗恒正由返还率 <1 保证；balance-sim 三档可验证批量后吞吐提升。
