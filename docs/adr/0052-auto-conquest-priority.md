# 自动攻占目标按资源消耗优先

无限模式自动攻占（ADR-0033 `autoConquestTick`）发起前对**可立即发起**的生成军事目标按资源消耗升序排序——守卫（军力投入）升序为主序、快照资源费 `costMineral + costEnergy` 升序为平局打破——资源消耗更少的目标优先处理；既有语义（投满守卫、军力保底 10%、资源费不足暂停、仅生成目标、纯军力、60s 冷却）全部不变。

**状态**: Accepted（2026-08-11 用户需求）
**证据**: `src/engine/conquest.ts:219-255`（autoConquestTick 候选排序）；`src/engine/conquest.test.ts:199-293`（消耗优先测试组）；`src/engine/offline.ts:112-119`（离线复用同一函数）

## 背景

1. **自动攻占按发现顺序机械扫第一个可用目标**：`autoConquestTick` 遍历 `generatedTargets` 数组，对第一个 `kind='conquest'`、`status='available'`、未进行中且守卫 > 0 的目标投满守卫发起——不比较目标间的资源消耗。
2. **发现顺序 ≠ 消耗顺序**：生成军事目标守卫 = `min(max(500, ⌊名义产能×40s⌋), ⌊军力上限/3⌋, ⌊名义产能×180s⌋)`（ADR-0033 + 0051），随当期产能/容量动态变化；目标另带 ADR-0028 快照资源费 `costMineral`/`costEnergy`。先发现的目标可能恰好高消耗，自动攻占照打，军力/矿/能白白多耗。

## 决策

1. **候选排序**：`autoConquestTick` 先 `filter` 出「可立即发起」候选（`generatedTargets` 中 `kind='conquest'`、`status='available'`、`startedAt==null`、守卫 > 0），再按 `(guard, costMineral+costEnergy)` 升序 `sort`，然后对排序后候选执行原守卫/保底/`startConquest`/`pausedAt` 逻辑。
2. **排序键**：主序 = 守卫（军力投入，每次自动攻占恒全额消耗）；次级 = `costMineral + costEnergy`（快照资源费，同守卫时的确定性平局打破，覆盖矿/能消耗）。
3. **稳定性**：`Array.prototype.sort` 稳定（ES2019+）——等键候选保持数组顺序（先发现者优先）；`filter` 产生新数组，**不改 `generatedTargets` 展示顺序**（UI 列表仍按发现顺序）。
4. **离线继承**：`settleOffline` 按 60s 冷却周期批量调用 `autoConquestTick`（`offline.ts:112-119`），自动继承优先顺序。

## 为什么

- 用户要求「军事模块自动攻占应该优先处理消耗资源更少的目标」——先易后难的自动化策略：低守卫目标回充快、可更早滚动收益；高守卫目标留到军力/经济更充裕时处理。
- 排序键选守卫为主序：自动攻占恒投满守卫（军力是每次必耗、且是保底/门槛的资源）；矿/能费为条件性消耗且不同量纲，作次级平局打破而非主序。
- 只改选择顺序、不动公式：守卫/资源费生成（ADR-0028/0033/0051）、保底、暂停、范围语义均不受影响，改动面最小。

## 后果

- **行为变化**：多目标可用时自动攻占先处理低守卫目标，再逐步处理高守卫目标；同守卫时先处理低资源费目标。
- **UI**：军事页目标列表展示顺序不变（仍按发现顺序）；自动攻占开关/状态显示无变化。
- **测试**：`conquest.test.ts` +5（守卫主序首 tick / 次 tick / 进行中跳过 / 资源费平局打破 / 离线批量按序发起）；全量 1004 测试通过。
- **无 schema / i18n / balance 常量变更**；无新导出。
